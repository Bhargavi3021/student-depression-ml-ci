Why Kubernetes Is NeededDocker packages the Student Result Prediction application into a portable image, but Docker alone does not provide a complete mechanism for managing many running container instances, maintaining a desired replica count, replacing failed instances, exposing a stable service endpoint, or coordinating rolling updates. Kubernetes adds these container-orchestration capabilities.Classroom one-line explanation: Kubernetes is used to deploy, manage, scale, update, and automatically recover the Dockerized Student Result Prediction application.5. Kubernetes vs Apache AirflowApache AirflowKubernetesOrchestrates workflow tasks arranged as DAGs.Orchestrates containers and deployed applications.Answers: Which ML task should run first, next, or after a failure?Answers: How many application instances should run, how are they exposed, and what happens when one fails?Example: load data -> preprocess -> train -> evaluate.Example: Docker image -> Pods -> Service -> replicas -> rolling update.Handles task dependencies, schedules, retries, and DAG logs.Handles Pods, Services, replica management, health probes, scaling, updates, and recovery.Primarily supports workflow/pipeline execution.Primarily supports deployment/runtime infrastructure.Key distinction: Airflow orchestrates workflows; Kubernetes orchestrates containers. They can be used together in a larger MLOps platform, but they solve different problems.6. Kubernetes Objects UsedObjectPurpose in this practicalClusterThe Minikube Kubernetes environment in which the application runs.DeploymentDeclares the desired Student Result Prediction application state and manages ReplicaSets.ReplicaSetMaintains the requested number of Pod replicas for the Deployment.PodRuns one instance of the Student Result Prediction container.ServiceProvides a stable network endpoint in front of the Pods.Readiness probeChecks whether a Pod is ready to receive traffic.Liveness probeChecks whether a running container is still healthy and should be restarted if repeatedly unhealthy.Rolling updateGradually replaces old Pods with Pods using a newer image.RollbackRestores the Deployment to an earlier revision if the new release is unsuitable.8. Step-by-Step ProcedureStep 1 - Verify Docker, Minikube, and kubectlOpen PowerShell, Terminal, or the command shell used for the previous Docker practicals. Verify the required tools:docker --versionminikube versionkubectl version --clientExpected resultDocker, Minikube, and kubectl report their versions without command-not-found errors.Step 2 - Start the Local Kubernetes ClusterFor a classroom machine using Docker Desktop as the container runtime, start Minikube with the Docker driver:minikube start --driver=dockerIf the cluster already exists, Minikube reuses the existing profile unless another profile is selected.Expected resultMinikube completes startup and reports that kubectl is configured to use the Minikube cluster.Step 3 - Verify the Clusterkubectl cluster-infokubectl get nodeskubectl config current-contextExpected resultAt least one Kubernetes node is listed in Ready state and the active context points to the intended local cluster.Step 4 - Create the Practical-13 Working Foldermkdir Practical_13_Kubernetescd Practical_13_KubernetesCreate two manifest files inside the folder:Practical_13_Kubernetes/├── deployment.yaml└── service.yamlStep 5 - Identify the GHCR Image and TagOpen the GHCR package created in Practical-8/Practical-9 and identify an image that already passed the CI container tests. Replace placeholders in this practical with the actual repository owner and image tag.ghcr.io/<github-username>/student-result-prediction:<IMAGE_TAG>Recommended practice: Use a versioned or commit-SHA image tag when demonstrating updates. A fixed tag makes it clear exactly which container version Kubernetes is running.Step 6 - Configure Access if the GHCR Package Is PrivateIf the GHCR image is public, skip this step. If the package is private, create a Kubernetes registry Secret using a credential that can read the package:kubectl create secret docker-registry ghcr-secret --docker-server=ghcr.io --docker-username=<github-username> --docker-password=<REGISTRY_READ_TOKEN> --docker-email=<email>Attach the registry Secret to the default ServiceAccount used by Pods in this classroom namespace:kubectl patch serviceaccount default -p '{"imagePullSecrets":[{"name":"ghcr-secret"}]}'Verify only the Secret name; do not display or capture token contents:kubectl get secret ghcr-secretExpected resultThe Secret exists and new Pods can authenticate to the private GHCR package without storing the token in the YAML file.Step 7 - Create deployment.yamlCreate deployment.yaml and replace the image placeholder with the tested GHCR image and selected tag:apiVersion: apps/v1kind: Deploymentmetadata:  name: student-result-prediction  labels:    app: student-result-predictionspec:  replicas: 1  selector:    matchLabels:      app: student-result-prediction  strategy:    type: RollingUpdate    rollingUpdate:      maxUnavailable: 0      maxSurge: 1  template:    metadata:      labels:        app: student-result-prediction    spec:      containers:        - name: student-result-api          image: ghcr.io/<github-username>/student-result-prediction:<IMAGE_TAG>          imagePullPolicy: Always          ports:            - containerPort: 8000          readinessProbe:            httpGet:              path: /health              port: 8000            initialDelaySeconds: 10            periodSeconds: 10            timeoutSeconds: 3            failureThreshold: 3          livenessProbe:            httpGet:              path: /health              port: 8000            initialDelaySeconds: 30            periodSeconds: 20            timeoutSeconds: 3            failureThreshold: 3          resources:            requests:              cpu: "100m"              memory: "128Mi"            limits:              cpu: "500m"              memory: "512Mi"The probes reuse the /health endpoint already tested in the earlier practicals. The resource values are classroom defaults and may be adjusted if the model requires more memory or CPU.Step 8 - Create service.yamlCreate service.yaml to provide a stable endpoint in front of the Pods:apiVersion: v1kind: Servicemetadata:  name: student-result-prediction-service  labels:    app: student-result-predictionspec:  type: NodePort  selector:    app: student-result-prediction  ports:    - name: http      protocol: TCP      port: 80      targetPort: 8000The Service listens on port 80 inside the cluster and forwards requests to port 8000 in whichever ready Pod receives the traffic.Step 9 - Apply the Kubernetes Manifestskubectl apply -f deployment.yamlkubectl apply -f service.yamlExpected resultKubernetes reports that the Deployment and Service were created or configured successfully.Step 10 - Wait for the Deployment to Become Readykubectl rollout status deployment/student-result-predictionkubectl get deploymentskubectl get podskubectl get servicesExpected resultThe Deployment shows one available replica, one Pod reaches Running/Ready state, and the NodePort Service is listed.Step 11 - Inspect the Deployment and Pod Detailskubectl describe deployment student-result-predictionkubectl get pods -o wideCheck the selected image, replica count, Pod status, node, restart count, readiness, and recent events.Step 12 - Access the Student Result Prediction ServiceAsk Minikube to expose the NodePort Service through an accessible local URL:minikube service student-result-prediction-service --urlCopy the URL shown by Minikube. Depending on the operating system and driver, the command may maintain a tunnel while the terminal remains open. Keep that terminal running during testing.Example only:http://127.0.0.1:xxxxxExpected resultA local URL is available for reaching the Kubernetes Service.Step 13 - Test /health, /docs, /predict, and /metricsUsing the URL returned by Minikube, test the same endpoints already used in previous practicals:<SERVICE_URL>/health<SERVICE_URL>/docs<SERVICE_URL>/metricsUse Swagger at /docs to submit a valid Student Result Prediction request to /predict using the existing project schema. Do not invent new fields or retrain the model.Expected resultThe health check succeeds, Swagger opens, the prediction endpoint returns a valid response, and the Prometheus metrics endpoint remains available.Step 14 - Inspect Application Logs from KubernetesList the Pod name and then inspect the logs produced by the Practical-11 logging implementation:kubectl get podskubectl logs <pod-name>To follow new requests in real time:kubectl logs -f <pod-name>Expected resultStartup, health, prediction, and request logs are visible from the container running inside the Kubernetes Pod.Step 15 - Scale the Deployment to Three Replicaskubectl scale deployment student-result-prediction --replicas=3kubectl get deployment student-result-predictionkubectl get pods -o wideExpected resultThree Student Result Prediction Pods reach Running/Ready state while the Service name and access method remain unchanged.Step 16 - Verify That the Service Has Multiple Ready BackendsKubernetes creates EndpointSlices for the ready Pods selected by the Service. Inspect them with:kubectl get endpointslice -l kubernetes.io/service-name=student-result-prediction-service -o wideThe output should contain multiple backend addresses when all three Pods are ready.Main idea: Clients use one stable Service endpoint. Kubernetes routes that service traffic to ready Pod replicas behind it.Step 17 - Demonstrate Kubernetes Self-HealingRecord the current Pod names:kubectl get podsDelete one running Pod intentionally:kubectl delete pod <one-pod-name>Immediately observe the Pod list:kubectl get pods -wStop the watch with Ctrl+C after a replacement Pod reaches Running/Ready state.Expected resultThe deleted Pod disappears and the Deployment/ReplicaSet automatically creates a replacement so the desired replica count returns to three.Step 18 - Verify the Application After Pod RecoveryCall /health and /predict again through the same Service URL.Expected resultThe Student Result Prediction API remains accessible through the Service after the deleted Pod is replaced.Step 19 - Prepare a New Tested Image for the Rolling-Update DemonstrationUse a newer Student Result Prediction image that has already passed the Practical-9 GitHub Actions build/test workflow and has been published to GHCR. The change may be a harmless version/message update; the ML model itself does not need to be retrained unless that is part of the approved code change.ghcr.io/<github-username>/student-result-prediction:<NEW_IMAGE_TAG>Important: Do not perform a Kubernetes update to an image that failed CI. The same principle used throughout the series remains: only tested artifacts progress toward deployment.Step 20 - Perform a Rolling UpdateReplace <NEW_IMAGE_TAG> with the actual newer tested tag:kubectl set image deployment/student-result-prediction student-result-api=ghcr.io/<github-username>/student-result-prediction:<NEW_IMAGE_TAG>kubectl rollout status deployment/student-result-predictionObserve Pods during the update in another terminal if required:kubectl get pods -wExpected resultKubernetes gradually creates Pods with the new image and removes old Pods while maintaining the Deployment according to the rolling-update strategy.Step 21 - Verify the New Image and Rollout Historykubectl get deployment student-result-prediction -o widekubectl rollout history deployment/student-result-predictionkubectl get pods -o wideTest /health, /predict, and /metrics again through the Service URL.Expected resultThe Deployment is available with the new image and the Student Result Prediction API remains functional.Step 22 - Demonstrate RollbackFor classroom demonstration, roll the Deployment back to the previous revision:kubectl rollout undo deployment/student-result-predictionkubectl rollout status deployment/student-result-predictionkubectl rollout history deployment/student-result-predictionVerify the active image after rollback:kubectl get deployment student-result-prediction -o jsonpath='{.spec.template.spec.containers[0].image}'Expected resultKubernetes returns the Deployment to the previous image revision and the service becomes ready again.Step 23 - Scale Back to One Replicakubectl scale deployment student-result-prediction --replicas=1kubectl get podsExpected resultOnly one application Pod remains after Kubernetes completes the scale-down.Step 24 - Optional: Inspect Resource UsageIf the Minikube metrics-server add-on is available, enable it and inspect basic CPU/memory usage:minikube addons enable metrics-server# Wait briefly for metrics collectionkubectl top podsThis is Kubernetes resource usage and is separate from the application-level Prometheus metrics introduced in Practical-12.Step 25 - Common TroubleshootingProblemLikely causeSuggested fixminikube start failsDocker is not running or the selected driver is unavailable.Start Docker Desktop/Engine and retry with the approved driver.ImagePullBackOffWrong GHCR image/tag, private package without credentials, or invalid registry access.Verify the image path/tag. For a private package, recreate ghcr-secret with a valid read credential and inspect Pod events.ErrImagePullKubernetes cannot pull the referenced image.Check spelling, tag existence, package visibility, network access, and registry authentication.CrashLoopBackOffThe container starts and repeatedly exits.Use kubectl logs and kubectl describe pod to inspect the application error and events.Pod not Ready/health probe is failing or startup needs more time.Test the image locally, inspect logs, verify port 8000, and adjust probe timing if startup is legitimately slow.Service URL does not openMinikube tunnel/service command is not active or Service/Pods are not ready.Re-run minikube service ... --url, keep the tunnel terminal open, and check Service endpoints./predict fails but /health worksApplication input or model-serving logic issue.Use the same valid payload from earlier practicals and inspect container logs.Only one Pod after scale commandDeployment has not completed scaling or new Pods cannot start.Run kubectl get pods and kubectl describe deployment to inspect events.Deleted Pod does not returnDeployment desired replica count may be zero/incorrect or scheduling/pull errors exist.Check kubectl get deployment, ReplicaSet status, and events.Rolling update is stuckNew image cannot start or readiness probe fails.Inspect new Pod logs/events; correct the image and use rollout undo if needed.kubectl top pods failsmetrics-server is not installed or not ready.Enable the Minikube metrics-server add-on and wait for metric collection.13.
